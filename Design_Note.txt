Design Note — MVP, Flow, Classes & Trade-offs 
 
MVP 
The MVP is basically a place where someone can practice an LLD problem and receive feedback on their answers. 
The main flow is: 
Problems → Choose Problem → Start Attempt → Write Solution → Submit → AI Evaluation → Feedback 
I divided the solution into a few simple sections such as assumptions, classes, responsibilities, relationships, abstractions, design decisions, and extensibility. This makes it easier for the learner to think about the design step by step. 
 
Main classes / parts 
I have kept the backend around a few main concepts: 
Problem – stores the LLD question. 
Attempt – represents a learner working on a particular problem. 
Submission – stores the learner's actual answer. 
Evaluation – stores the results of the evaluation. 
Feedback – contains detailed feedback for different parts of the answer. 
The frontend is built with Next.js and the backend with NestJS. PostgreSQL is used for storing the application data. 
 
AI part 
For the AI feedback, I used the Gemini API. 
I sent the problem and the learner's submitted design to Gemini and asked it to review the answer. The response is then shown to the learner as feedback. 
I intentionally kept this part simple for the MVP. I didn't try to build my own AI model or anything like that. The main focus was using the available AI API in a useful way. 
 
Trade-offs 
One trade-off was keeping the submission as structured text instead of trying to build a complete diagram editor. A diagram editor would be interesting, but it would have made the project much bigger. 
I also kept the evaluation fairly straightforward. It gives useful feedback, but it should not be treated as the final authority on whether a design is correct. LLD can have multiple reasonable solutions.
